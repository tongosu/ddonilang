# 첫 일차방정식 풀이 작성

범위는 가정 `1+(3/2)t=7` 아래의 조건부 풀이 한 개다. 해 전체의 존재·유일성이나 무가정 정리 발급이 아니다. 정확한 유리수에서 같은 연산을 양쪽에 적용하고 양쪽 항을 각각 검사하는 이유를 설명한다.

정상 기대: 양변1빼기→양쪽 정리 `(3/2)t=6`→비영 계수3/2나누기→양쪽 정리 `t=4`. 한 화면의 조작은 실제 원문에서 조작+정리 두 단계다. 두 단계 모두 전체 원문에 보이고 실제 checker의 검사 대상이어야 한다.

중간 오류 기대: 오른쪽6을5로 바꾸면 그 정리에서 처음 거부해야 한다. 나중 답4로 중간 오류를 숨길 수 없다. 후속 단계는 실제 관찰에 따라 미검사로 구분한다. 0나누기는 조작 거부이며 no_solution·non_unique·도구 예산 소진과 구별한다. 진단 이름/위치는 고정 생산자 관측을 공급받기 전 만들지 않는다.

현재 수업의 풀이.ddn·중간오류.ddn·영나누기.ddn은 실제 브라우저에서 입력·검사한 원문이다. Native 입구용 root/main과 조건부 풀이 파일을 분리한다. 움직씨 시작 정의를 풀이 파일에 함께 넣은 최초 시도는 `E_PROOF_DEFINITION`으로 분석 거부됐으므로 이 실패를 보존하고 실제 작품에서 파일을 분리했다. 검사 시 테스트용으로 코드를 잘라 내지 않는다.

고정 생산자 SOURCE9792e3880515711976f9b7c608da4190e3f02a47/PRODUCT30485a9b36a47b89b2c7b5c3d0e91d21f5fecce7의 실제 Worker/WASM으로 정상·6→5·0·수정 후 정상·입력 보조의 명명 결과자리를 검사했다. 입력 보조는 조작+정리 두 줄을 그대로 적으며, 마지막 이름있는 결과자리에는 체크박스로 `<-`를 선택한다. 별도 수학 parser·JS 검산·입력 교정·숨은 올바른 단계 삽입은 없다.

브라우저 textarea가 제공하는 실제 LF 원문을 그대로 검사CLI/Node에도 전달해 판정·거부 코드와 Node/브라우저 전체 관찰JSON을 대조했다. 공급자의 원래 CRLF raw와 전체 바이트가 같다고 하지 않는다. 현재 실제 원문의 위치는 중간 오류4줄39열,0계수5줄23열이며, 줄바꿈/원문이 달라지면 실제 새 span을 사용한다. UTF-8 범위를 임의 보정하지 않는다.

학생이 문제·근거를 읽고 예측하는 것, 조작을 고르는 것, 첫 잘못을 설명하고 고치는 것을 구분한다. 소비자 집중9개와 실제 브라우저 조작은 학생/Human 성공이 아니다. 실제 Worker 응답을 지연한 뒤 편집했을 때 옛 결과가 게시되지 않음을 확인했다. 분석 실패에는 checked prefix가 없고 최종 목표 오류는 모든 단계가checked여도 전체 rejected일 수 있다. 해당 고정 응답을 소비자 검사에 재사용하며 새 성공을 합성하지 않는다.

기존 V3 A/B·음수 검산·V2 보임 저장 근거는 변경 없는 부분만 재사용한다. plan의 순서 정정에 따라 이번 반환은 실제 web·노트·편집 연결까지이며 V4 Native admission·저장/cold·명시재검사는 NOT_RUN이다. dev가 같은 SOURCE로 최종 결합한 실행물을 공급한 뒤 남은 해당 검사만 수행한다. 이번 검사용 Native 호스트는 고정 소스9792로 별도 준비했지만 배포/최종 결합 제품으로 승격하지 않는다. r012를9792로 표시하지 않는다.

예전 *_후보.ddn 세 파일은 준비 이력이며 공식 실습 링크에서 제외했다. 수업 진입점의 현재 원문 세 파일을 사용한다. catalog 공통 파일은 이번 배정 밖이라 공식 목록 추가를 주장하지 않는다. 새 외부 자료·그림·라이선스는 사용하지 않았고 기존 프로젝트 고지를 유지한다.
