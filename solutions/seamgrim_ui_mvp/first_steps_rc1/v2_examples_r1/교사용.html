도우미 판본과 보임 원문 보관

V2-01: 각 작품이 판본을 선택한다

선수는 기존18·19차시의 모듈과 별칭,30차시의 저장이다. 공식 생산자/소비자 예제 두 개를 재사용하며 A와 B는 소비자를 각각 복제한다. 새 판본 발행은 선반을 바꾸고, 명시 갱신은 선택 작품의 의존을 바꾼다. 원문 저장과 실행은 또 다른 단계다.

기대는 A7/B8 → 새 판본 발행만으로7/8 유지 → A만 갱신9/8 → B도 갱신9/10이다. 학생에게 예상값만 말하게 하지 말고 실제 선택 판본과 결과를 함께 가리키게 한다. 설치 전 소비자의 출력1을 판본 선택의 성공으로 세지 않는다.

r176은 단일 closed helper6파일의 CLI3/WASM/Chrome·저장/cold·누락/낡은 lock 거부 근거다. 변경분 한정 독립 PASS는 있지만 A/B 전체 독립 실행으로 확대하지 않는다. 영구ID 작품의 선반 갱신은 r187 후속 수정이 별도로 있으므로, r176만으로 저장 후 A/B 갱신 수업을 완료 처리하지 않는다. 이 후보는 r187 교정과 그 실제 A/B·cold 근거를 인수했다. 새 교육 진입 영향 확인은 별도로 결속하며 과거 독립 PASS를 자동 상속하지 않는다.

거부 실험은 배포 학생 정상본이 아닌 분리된 임시 실습 사본에서 한다. 누락 helper는 작성 frontdoor 거부, stale lock은 실제 원문 갱신의 lock 거부, Chrome 원문 불일치는 선행 source guard다. ConflictingRetry를 lock 검증으로 오인하지 않는다. 손상 데이터를 고쳐 억지 통과시키지 말고 정상 고정본을 명시 재선택한다.

V2-03: 파일 보존은 검사의 대체물이 아니다

선수는 기존14차시의 셈씨,17차시의 진단,29·30차시의 저장이다. 정상 예제는 같은 근거를 전달하는 대수 정의 하나와 항등구조 법칙을 전달하는 정의 둘이다. 각각 조건부 수용1·2가 기대이며 무가정 증명 발급이 아니다.

받는 근거, 결과 목표, 본문의 반환을 학생이 짚게 한다. 같은 내용이 저장됐더라도 새 프로세스에서 검사 상태는 미검사다. 명시 검사 뒤 조건부 수용으로 바뀌어야 한다. 원문 수정을 하면 이전 결과가 최신 판본을 대신하지 않음을 확인한다. proof handle의 영구 보존을 요구하지 않는다.

잘못된 목표 binder의 실제 Native 저장 거부 근거를 재사용한다. 학생의 새 이름 수정 활동은 그 반례와 같은 부류지만 최종 교육 UI에서 새로 실행한 것으로 기록하지 않는다. 브라우저 편집→저장 거부→수정→재검사 영향은 dev 최종 연결 후 확인할 항목이다.

4abd1262의 원문·실행물은 debug Native/release WASM의 개발 고정물이다. 같은 버전 숫자의 r176 ZIP을 대신 쓰지 않는다. 구형 reader의 오류는 호환 거부 관측이지 새 reader가 구조 저장을 못 한다는 뜻이 아니다. 성공 JSON이나 별도 텍스트를 검사 근거로 공급하지 않는다.

학생의 설명을 확인할 질문

  • 새 판본을 발행했는데 B가 그대로여야 하는 이유는?
  • 현재 결과가 어느 원문·판본을 사용했는가?
  • 보임 파일을 다시 열었을 때 ‘미검사’가 왜 정상인가?
  • 계산의 출력5, 대입 검산 참, 조건부 정의 수용은 각각 무엇인가?
  • 실패한 저장 뒤 원래 정상본이 보존됐는가?

실제 학생0/HUMAN_NOT_RUN. 작성자 근거 재사용·교육 연결 확인·독립검토·배포를 분리한다. 물리 OS IME와 모든 CLI 이름의 교재 실행을 새로 확인한 것으로 쓰지 않는다.
