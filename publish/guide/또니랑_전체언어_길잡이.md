# 1. 한국어로 프로그램의 뜻을 적기

또니랑은 초등학교 졸업 전에 기억으로 남는 작품을 만들고 싶다는 생각에서 시작했습니다. 영어 명령을 한국어로 바꾸는 데서 더 나아가, 계산의 뜻과 값의 역할을 자기 말로 설명하고 적는 언어를 목표로 합니다.

```ddn
3 + 4 보여주기.
```

이 문장은 계산한 값을 보여 달라는 뜻입니다. 마침표는 문장의 끝입니다. 줄을 바꾸는 것과 문장을 끝내는 것은 다릅니다. 이름은 프로그램을 읽는 사람에게도 설명이 됩니다. `a`보다 `합계`, `가격`, `속도`가 도움이 되는 때가 많습니다.

한국어처럼 읽힌다고 컴퓨터가 상식으로 빈 뜻을 채우지는 않습니다. 이름과 씨, 받는자리, 등록된 호출 형태가 맞아야 합니다. 비슷한 이름이 둘이라면 먼저 나온 것을 고르지 않고 모호함을 알립니다.

생각해 보기: `결과`라는 이름과 `총요금`이라는 이름 중 어느 쪽이 계산의 목적을 더 잘 보여 주나요?

# 2. 값, 씨, 정의와 결속

**값**은 계산하거나 전달하는 대상입니다. **씨**는 어떤 종류의 값인지와 가능한 연산을 나타냅니다. 수, 글, 참거짓은 서로 다른 종류입니다. 숫자처럼 보이는 글도 저절로 수가 되지는 않습니다.

```ddn
기준 := 10.
현재 <- 기준.
현재 <- 현재 + 1.
현재 보여주기.
```

`:=`는 이름 있는 정의를 만듭니다. `<-`는 보통 결속과 다시결속을 맡습니다. `<-`로 처음 결속하는 것도 의미에 포함됩니다. 따라서 둘을 단순히 ‘처음 만드는 기호’와 ‘나중에 바꾸는 기호’로 외우면 안 됩니다.

정의에는 이름의 정체와 계약이 있고, 결속에는 현재 값이 있습니다. 정의의 종류와 범위별 다시결속 가능성은 해당 계약을 따라야 하며, 모든 지역 `:=`를 무조건 불변이라고 넓혀 설명하지 않습니다.

값의 종류를 정한 뒤 다른 종류를 조용히 넣지 않는 것은 실수를 일찍 발견하는 데 도움이 됩니다. 요금에 글을 더했다면 억지로 변환해 계산하기보다 어느 값이 잘못 전달됐는지 살펴봐야 합니다.

# 3. 셈씨와 움직씨

**셈씨**는 값을 계산하는 책임을, **움직씨**는 일을 수행하는 책임을 나타냅니다. ‘함수’를 만드는 방법만 외우기보다 무엇을 계산하고 무엇을 바꾸는지 먼저 나눕니다.

```ddn
(값:수~의) 두배:수:셈씨 := {
    두배 <- 값 * 2.
}.
7의 두배 보여주기.
```

이 예의 머리는 받는 값과 씨, 조사, 이름, 결과씨, 선언 종류를 적습니다. 본문에서는 `두배`라는 **결과자리**에 값을 놓습니다. 이것은 정의 자체를 바꾸는 결속이 아닙니다. 호출할 때마다 결과자리가 따로 생깁니다.

결과자리에 놓았다고 곧바로 함수가 끝나지는 않습니다. 뒤 문장이 있으면 계속 실행됩니다. 결과가 필요한 정의는 정상 종료하는 모든 길에서 결과를 정해야 합니다. 반복이 한 번도 실행되지 않을 수 있다면 그 반복 안에서만 결과를 정하는 것으로는 부족합니다.

움직씨는 출력이나 세계 변경 같은 일을 묶습니다. 프로젝트의 시작 정의도 이런 역할을 맡을 수 있습니다. 다만 작은 한 파일 프로그램을 쓰기 위해 항상 `실행` 움직씨로 감쌀 필요는 없습니다.

`-->`는 받는 씨와 내는 씨를 잇는 함수 형·서명의 표기이고, 정의를 만드는 기호는 `:=`입니다. 익명 함수값을 만드는 `|->`도 이름 있는 정의와 구분합니다.

# 4. 조사형 호출과 이름 인자

조사는 받는자리와 전달값의 관계를 읽게 합니다. `7의 두배`는 자연스럽게 읽히는 호출입니다. 조사형 호출이라고 인자 묶음 괄호가 항상 필요한 것은 아닙니다.

그러나 값이 여럿이면 한국어가 자연스러운지만으로 충분하지 않습니다. 밑변과 높이를 받는 계산을 `8을 5와 삼각형넓이`처럼 적으면 역할이 흐릿합니다. 이런 경우 이름 인자가 더 분명합니다.

```ddn
(밑변=8, 높이=5) 삼각형넓이 보여주기.
```

이는 `삼각형넓이`가 그 두 받는자리를 갖도록 정의되어 있다는 전제의 호출 예입니다. 선언하지 않은 이름이나 조사를 컴퓨터가 알아서 만들어 주지는 않습니다. 계산 이름에 무조건 `하기`를 붙이지도 않습니다. 계산은 계산답게, 수행하는 일은 일답게 이름을 고릅니다.

받는자리의 이름과 본문 안에서 쓰는 지역 이름은 역할이 다릅니다. 여러 호출 표면이 같은 정의를 가리키더라도 새 정의가 생기는 것은 아닙니다. 반대로 비슷한 한국어 표현이라고 자동으로 같은 정의가 되지도 않습니다.

인자 식은 원문에 적힌 순서로 평가됩니다. 조사나 이름으로 자리를 맞춘다고 계산 순서까지 바꾸지는 않습니다.

# 5. 조건과 반복

조건은 한 번 판단해 길을 고르고, 반복은 조건이 참인 동안 문장을 되풀이합니다.

```ddn
점수 <- 82.
{ 점수 >= 80 }이면 {
    "통과" 보여주기.
} 아니면 {
    "다시 도전" 보여주기.
}.
```

```ddn
횟수 <- 0.
{ 횟수 < 3 }인 동안 {
    횟수 보여주기.
    횟수 <- 횟수 + 1.
}.
```

반복을 쓸 때는 처음 값, 매번 바뀌는 값, 끝나는 조건을 찾아봅니다. `그리고`와 `또는`의 단락 평가는 앞의 값으로 결과가 정해지면 뒤 식을 평가하지 않습니다. 없는 원소를 읽기 전에 길이를 확인하는 식의 보호 조건에 중요합니다.

일차함수의 점들을 한 번 계산하는 일과, 세계가 한 마디씩 변하는 일은 다릅니다. 정적인 계산을 매마디 반복할 이유는 없습니다. 마찬가지로 항상 참인 조건으로 본문을 감싸는 것도 필요한 구조가 아닙니다.

순회는 대상의 각 항목을 다루는 흐름입니다. 항목의 씨와 결속 이름이 분명해야 하며, 이름에 `들`을 붙였다고 저절로 목록이나 순회 대상이 되지는 않습니다.

# 6. 여러 값을 담고 고르기

차림은 순서가 있는 같은 종류의 값들을 담습니다. 값꾸러미는 위치마다 다른 종류를 담을 수 있고, 묶음씨는 이름 있는 필드를 한 값으로 묶습니다. 고름씨는 여러 갈래 중 하나를 나타냅니다. 이 구조들은 모두 ‘상자’처럼 보여도 고르는 규칙이 다릅니다.

```ddn
점수들 <- 차림[70, 80, 90].
점수들[0] 보여주기.
점수들[1] <- 85.
```

차림 위치는 0부터 셉니다. `[1]`은 둘째입니다. 범위 밖 선택을 마지막 원소나 0으로 대신하지 않습니다. 범위는 시작을 포함하고 끝을 제외하는 반열림 규칙으로 읽습니다.

짝맞춤은 열쇠로 값을 찾습니다. 없는 열쇠를 엄격 선택하면 실패합니다. 안전 조회 `찾기`는 값의 있음과 없음을 `(T)있없`으로 구분해 돌려주는 별도의 연산입니다. ‘없음’과 정상값 0 또는 빈 글은 같은 뜻이 아닙니다.

글의 한 글자 선택은 사람이 읽는 글자 덩어리인 grapheme cluster를 기준으로 합니다. 바이트 수나 유니코드 코드 포인트 수를 글자 수로 몰래 대신하지 않습니다.

항목을 다시 놓는 것은 새 구조값을 만들고 뿌리 자리에 다시 결속하는 의미입니다. 이를 중간 삽입·삭제·길이 변경까지 하는 연산으로 해석하지 않습니다. 고름씨의 갈래도 숫자 위치로 고르는 목록 원소가 아니라 소유씨에 결속된 갈래입니다.

# 7. 실패를 값과 실행 오류로 구분하기

사용자가 복구할 수 있는 실패는 정상 계산의 결과값으로 나타낼 수 있습니다. 성공과 이유 있는 실패를 구분하는 `맺음`이 이런 역할을 맡습니다.

```text
맺음.$잘됨(값)
맺음.$안됨(까닭)
```

위는 갈래의 역할을 설명하는 골격입니다. 어떤 값과 까닭을 담을지는 선언한 씨에 맞아야 합니다. `해보고 안되면`은 복구 가능한 실패를 처리하고, `그대로둠`은 이미 있던 결속을 조건부 실패 때 보존하는 흐름입니다.

0으로 나누기, 손상된 증거, 권한 위반, 강제 중지처럼 실행 계약을 깨는 실패까지 정상 실패값으로 덮어서는 안 됩니다. 실패한 세계 변경을 반만 게시하거나 성공 결과처럼 남기지 않는 것도 중요합니다.

`마침.`은 현재 정의의 정상 흐름을 끝내는 표지입니다. 결과를 대신 만들거나 변경을 게시하는 표지가 아닙니다. 결과씨가 있다면 정상 종료 전에 그 결과가 준비되어 있어야 합니다.

# 8. 작품, 모듈과 가지

작품이 커지면 파일, 모듈, 외부 가지를 구분합니다. 파일은 원문이 있는 위치이고, 모듈은 정의의 소유와 공개 경계입니다. 가지는 재사용하는 꾸러미입니다. 가까운 폴더에 있다고 자동으로 같은 모듈이나 실행 뿌리가 되는 것은 아닙니다.

정식 뿌리는 `얽음`으로 작품을 묶고, `쓰임`과 `드러냄`은 가져오기와 공개 경계를 나타냅니다. 모듈의 머리는 하나이며 이 지시문을 올릴 위치가 됩니다. 시작은 로컬 모듈의 실행 가능한 정의를 가리킵니다. 시작을 생략했다고 첫 정의를 몰래 실행하지 않습니다.

**가지의 판본**과 **원문을 해석하는 글판**은 다른 축입니다. 꾸러미 버전이 같아도 문법을 해석하는 판은 별도로 결속해야 합니다. 한 파일 실행은 정식 작품 뿌리 없이 호출하는 쪽에서 명시적으로 글판을 정할 수 있습니다.

외부 가지도 이름만 같은 최신 내용을 받아 실행하면 재현이 깨집니다. 의존하는 내용과 계약을 정확히 결속하는 것이 저장과 다시 열기의 바탕입니다.

# 9. 입력, 상태와 마디

게임과 시뮬레이션은 입력을 받아 상태를 바꿉니다. **마디**는 세계가 정해진 순서로 진행하는 계산 단위입니다. 화면의 프레임, 풀이기의 내부 계산 단계, 세계의 마디는 같은 단위가 아닙니다.

키를 눌렀다는 사실과 세계의 행동도 구분합니다. ‘왼쪽으로 움직이기’라는 행동은 키보드, 화면 버튼, 다른 입력 장치로 만들 수 있습니다. 세계가 장치 이름 대신 논리 행동을 받게 하면 조작 방법을 바꿔도 규칙을 재사용할 수 있습니다.

시작 → 입력 결속 → 상태 변화 후보 계산 → 검사 → 게시라는 경계로 생각해 봅니다. 계산 중 실패하면 후보를 버리고 이전 상태를 유지해야 합니다. 두 전이가 동시에 가능할 때 먼저 발견한 하나를 임의로 택하는 것도 피합니다.

화면을 빨리 재생하거나 천천히 재생한다고 세계 시간이 달라져서는 안 됩니다. 실제 경과 시간은 표시와 진행 요청에 쓰더라도 세계 계산의 숨은 입력이 되어서는 안 됩니다.

# 10. 보개와 셈그림

`보여주기`는 값을 출력하는 일입니다. 보개는 계산을 사람이 이해할 수 있도록 표, 그래프, 장면 등으로 구성하는 층입니다. 셈그림은 원문을 고치고 그 결과를 살펴보는 작업대입니다.

보개짜임은 네 관계로 생각할 수 있습니다.

- **으뜸:** 짜임의 기본 보기. 짜임마다 하나이며 닫지 않습니다.
- **겹:** 같은 짜임의 으뜸 위에 추가 정보를 얹는 보기.
- **곁:** 옆이나 위아래에서 설명·다른 그래프·다른 관점을 보는 자리.
- **돋:** 대상을 선택해 여는 보기. 관계마다 한 번에 하나입니다.

포물선의 위치를 으뜸으로 보고 속도 벡터를 겹치고, x-t 그래프를 곁에서 보는 예를 생각할 수 있습니다. 진자라면 각도와 에너지를 함께 볼 수 있습니다. 이것은 보기의 역할 예시이지 새로운 선언 문법을 정하는 코드가 아닙니다.

같은 세계를 여러 관점으로 보고, 표현을 전환하고, 규칙과 조절값을 바꾸고, 대표 상황과 측정값을 비교하며 짧은 설명을 따라 실험하는 것이 목표입니다. 보기 버튼을 누르는 일 자체가 세계 상태를 바꾸지 않도록 경계를 둡니다.

원문이 선언한 궤적과 화면이 지난 그림을 쌓아 보여 주는 기록은 구분해야 합니다. 화면이 예제 이름만 보고 축·단위·속도를 추측하면 원문을 바꿔도 같은 그림이 나오는 문제가 생깁니다.

# 11. 수, 단위, 텐서와 모델

수치 계산에는 표현 범위, 반올림, 계산 방법이 있습니다. 화면에 출력하는 자릿수와 실행기가 계산에 쓰는 값도 다릅니다. 범위를 넘은 값을 조용히 잘라 정상값으로 만들지 않는 것이 중요합니다.

단위는 숫자 뒤의 장식이 아닙니다. 길이와 시간을 구분하고 어떤 연산이 가능한지 검사하는 정보입니다. 위치와 속도, 온도를 다룰 때 어떤 단위와 기준을 쓰는지 모델에 드러나야 합니다.

텐서는 원소씨와 정적인 축 크기 묶음을 가진 값입니다. 중첩 차림이 직사각형처럼 보인다고 자동으로 텐서가 되지는 않습니다. 벡터와 행렬이라는 수학적 역할도 단순히 1차원·2차원 텐서라는 이유만으로 붙지 않습니다.

```text
A[i,j]   한 번에 여러 축을 선택
A[i][j]  첫 선택의 결과를 다시 선택
```

두 표기는 전역적으로 같지 않습니다. 모든 축을 스칼라 위치로 골라 없애면 원소값이 나오지만, rank-0 텐서와 스칼라는 별개의 씨입니다. 슬라이스 교체는 같은 모양을 요구하며 크기 변경이나 자동 broadcasting을 숨기지 않습니다.

모델은 무엇을 계산하는지, 처음 상태, 계산 방법, 내놓을 값, 끝 조건과 오차 계약을 함께 읽는 구조입니다. 풀이기를 찾지 못했는데 다른 방법으로 몰래 바꾸면 같은 모델을 다시 확인하기 어렵습니다.

# 12. 수식, 명제와 증거

수식은 계산 구조이고, 명제는 참이라고 주장하는 내용이며, 증거는 그 주장을 확인할 근거입니다. 예쁘게 표시한 식이나 참인 Bool 하나가 형식 증명이 되지는 않습니다.

`수식{E}`는 수식 구조를, `세움{P}`는 명제 구조를 만듭니다. 이것만으로 계산이나 증명이 실행되지는 않습니다. 명시적인 `풀기`와 검사 과정이 별도의 책임을 맡습니다.

AI나 외부 계산기는 답과 증거 후보를 만들 수 있습니다. 최종 증거를 받아들이는 일은 독립 검사기가 맡습니다. 어떤 가정과 정의, 제공자, 검사 프로필을 사용했는지도 남겨야 합니다. 같은 결론이어도 가정이 다르면 같은 증명 문제로 보지 않습니다.

증명 판정의 네 갈래는 증명됨, 반증됨, 모름, 지원 밖입니다. 시간 초과나 잘못된 파일을 ‘반증됨’으로 바꾸지 않습니다. 반증에는 확인된 부정 증거나 반례가 필요합니다.

더 넓은 HoTT 축에서는 타입 사이의 길과 동치를 다룹니다. Proof의 같음 표지 `=:=`와 타입 값을 갖는 Path를 같은 것으로 합치지 않습니다. 이는 처음부터 모두 외우기 위한 내용보다, 계산의 답과 답의 근거를 구별하는 언어의 방향입니다.

# 13. 씨자리, 구실과 지음씨

씨자리는 여러 씨에 공통으로 적용할 정의의 자리를 나타냅니다. 구실은 그 씨가 갖춰야 할 행동을 나타냅니다. 단순히 이름만 바꿔 코드를 복사하는 대신, 무엇이 같고 무엇을 요구하는지 계약으로 묶습니다.

씨자리 추론은 실제로 결속된 필수 실행 입력을 근거로 합니다. 원하는 결과씨를 보고 숨은 씨를 맞추거나 AI가 적당한 답을 골라서는 안 됩니다. 해소되지 않음, 유일한 해소, 모호한 해소를 구분합니다.

지음씨는 작성·컴파일 단계에서 타입이 있는 선언보기를 읽고 선언묶음을 만드는 책임입니다. 아무 문자열을 만들어 다시 파싱하는 무제한 매크로와 다릅니다. 생성한 선언도 일반 선언과 같은 이름·씨·구실·효과·정본 검사를 거칩니다. 중간 생성이 실패하면 절반만 합치지 않습니다.

이런 기능은 반복되는 선언을 도와주지만 컴파일 중 시간, 네트워크, 세계 상태를 몰래 읽어 뜻을 바꾸는 통로가 되어서는 안 됩니다.

# 14. 글, 바이트와 말씨

사람이 읽는 글과 파일·통신의 바이트열은 다릅니다. UTF-8 변환도 명시적으로 다루며 잘못된 입력을 모르게 고치지 않습니다. 한 글자의 경계와 정규화 규칙이 고정되어야 같은 글을 같은 방식으로 선택할 수 있습니다.

글무늬는 글을 맞추고 찾고 나누고 바꾸는 계약입니다. 실행하는 컴퓨터의 정규식 기능을 통째로 물려받는 방식이 아닙니다. 말무늬는 등록된 자리와 정의에 결속된 문장 표면을 다루며, AI의 확신이나 사전 순위로 모호한 후보를 선택하지 않습니다.

다른 말씨로 작성하더라도 정의의 정체, 받는자리, 결과와 효과 계약은 보존되어야 합니다. 선언 투영은 구현 본문을 새로 번역하는 일과 다릅니다. 번역 문서 수, 지원 말씨 수, 실제 사용 검증도 서로 다른 수치입니다.

한국어가 출발점이라는 것은 다른 언어를 막는다는 뜻이 아닙니다. 어떤 표면으로 쓰든 같은 뜻으로 결속되었는지 확인할 기준을 갖겠다는 뜻입니다.

# 15. 자료, 기록과 AI

외부 자료는 내용뿐 아니라 출처와 판본이 중요합니다. 같은 파일 이름이라도 내용이 바뀌면 같은 실험 입력이 아닙니다. 경로와 수정 시각만으로 자료나 원문의 정체를 대신하지 않습니다.

봉인은 실행이 어떤 내용을 사용했는지 정확히 결속하는 일로 생각할 수 있습니다. 원문, 입력, 의존 가지, 실행계약과 자료의 관계가 있어야 결과를 다시 확인할 수 있습니다. 세계 해시 하나가 같다고 실행의 모든 조건이 같았다고 결론내리지는 않습니다.

세계가 읽은 입력은 기록이 담을 수 있어야 합니다. 키 이름이나 포인터 값을 읽은 실행을 그 값을 담지 못하는 기록으로 저장하고 같은 실행이라고 부르면 안 됩니다. 전체 입력의 동일성 검사와 제한된 호환 기록의 세계 결과 비교도 다른 주장입니다.

AI는 초안, 해설, 후보 계산과 증거를 만드는 협업자입니다. 사용자 승인, 언어 의미, 자료 출처나 증명 권한을 대신 만들지는 않습니다. 바깥에서 온 AI 결과를 세계의 입력으로 쓰려면 어떤 값을 넣었는지 명시적으로 결속해야 합니다.

# 16. 하나의 작품으로 연결하기

작은 상점 프로그램을 생각해 봅니다. 셈씨는 요금을 계산하고, 움직씨는 주문 진행을 맡습니다. 물품은 묶음씨로, 주문 결과는 고름씨로 나눌 수 있습니다. 여러 주문을 차림으로 담고 실패를 값으로 구분합니다.

더 넓히면 논리 행동을 받아 세계 상태를 바꾸고, 보개에서 가격과 재고를 살펴봅니다. 입력과 자료를 기록하면 다른 사람이 같은 조건으로 다시 계산할 수 있습니다. 모델을 바꾸어 비교하고, 필요하다면 계산 규칙의 성질을 증명하는 단계로 이어집니다.

이것이 모든 기능을 한꺼번에 배우라는 뜻은 아닙니다. 먼저 작은 프로그램을 제대로 쓰고, 필요가 생길 때 다음 개념을 붙입니다. 게임 전용 함수를 끝없이 추가하는 대신 여러 작품에 공통으로 쓸 수 있는 책임과 값의 구조를 찾습니다.

연습: 만들고 싶은 작품 하나를 고르고 다음을 적어 보세요. 들어오는 입력은 무엇인가요? 계산과 실행의 책임은 어떻게 나눌까요? 보려는 결과는 무엇인가요? 다른 사람이 다시 확인하려면 무엇을 남겨야 하나요?
